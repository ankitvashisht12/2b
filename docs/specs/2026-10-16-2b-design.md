# 2b — second brain for projects, tasks, and artifacts

Date: 2026-10-16. Status: approved.

## Problem

Agent work produces many notes, reports, and HTML explainers. Without a
standard, they end up spread across several folders with mixed naming
patterns, free-text status, and no index. Each chat needs the folder and the
rules again. Search needs an agent. Manual project tracking stops because it
takes too much effort.

## Goal

One store and one CLI. The user talks to an agent. The agent uses the CLI to
record and read state. The user can ask:

- What is active? What is paused or on hold, and why?
- What is due soon?
- What did I work on this week or this month?
- Where is the artifact about X?

Done means:

1. Existing artifact folders can be moved into the store, in projects that
   the user approved, with proof that no file was lost.
2. An agent in any repo can create, update, find, and summarize state with
   `2b` commands only, guided by the `2b` skill.
3. `2b dash` opens a local dashboard with a week picker.
4. A recurring task (for example the 19:00 daily digest) runs on schedule
   through `launchd`, and a failed run shows a notification and an error on
   the dashboard.

## Not in scope

- A full cron syntax. Schedules use the small format in "Recurring tasks".
- Recurring jobs on a machine other than this Mac.
- Writing outside the store, except recurring jobs the user defines.
- More than one user, cloud sync, or editing in the dashboard.
- Tickets below tasks.

## Locations

| What | Where |
|---|---|
| Code (CLI, dashboard, skill) | this repo |
| Data (the store) | `~/obsidian/2b/` by default |
| Override | `$TWOB_HOME`, else `~/.config/2b/config.json` `{ "home": "..." }` |

The data folder is its own git repo for history. Names use lowercase
letters, digits, hyphens, and dots only, so they sync safely.

## Store layout

```
~/obsidian/2b/
  rules.md                    global rules
  projects/<project-slug>/
    readme.md                 project record (frontmatter + description)
    log.md                    append-only project log
    rules.md                  project rules (optional)
    tasks/<yyyy-mm-dd-task-slug>/
      readme.md               task record (frontmatter + description)
      log.md                  append-only task log
      rules.md                task rules (optional)
      <artifacts>             any files (notes, reports, HTML)
  inbox/<yyyy-mm-dd-slug>.md  quick dumps with no project yet
  learnings/<yyyy-mm>/<yyyy-mm-dd-slug>.md
```

## Data model

All records are Markdown with YAML frontmatter. No database. The CLI reads
the files each time; at a few hundred records this is fast enough.

### Project — `projects/<slug>/readme.md`

```yaml
---
title: Search ranking
area: work                  # work | personal
status: paused              # active | paused | on-hold | done | archived
status-reason: Waiting for user feedback on v2
started: 2026-09-25
deadline: unknown           # yyyy-mm-dd or "unknown"
repos: [~/code/example-app]
prs: [https://github.com/org/repo/pull/101]
resources:
  - { title: Feedback call, path: ~/notes/meetings/feedback.md }
  - { title: Docs, url: https://example.com }
links:
  - { to: evaluation, type: related }
---
What the project is about and why it exists.
```

Rules:
- `status-reason` is required for `paused` and `on-hold`.
- A project can last for months.

### Task — `projects/<p>/tasks/<yyyy-mm-dd-slug>/readme.md`

```yaml
---
title: Rate limiter conflict recovery
status: done                # todo | doing | blocked | done | dropped
status-reason:              # required for blocked and dropped
started: 2026-10-15
due: 2026-10-17             # yyyy-mm-dd, "unknown", or empty
repo: ~/code/example-app
branch: fix/rate-limiter-retry
prs: [https://github.com/org/repo/pull/102]
resources: []
links:
  - { to: search-ranking/2026-10-14-ranking-drawer, type: depends-on }
artifacts:
  - path: scale-design.md
    title: Scaling across many orgs
    about: How the rate limiter behaves with many organizations
    why: User asked whether the fix holds at scale
    added: 2026-10-15
---
What the task delivers. Optional `- [ ]` checklist for steps.
```

A task has `kind: normal` (default) or `kind: recurring`. See
"Recurring tasks".

Rules:
- A task is the atomic unit. A task that grows too big is split into two
  linked tasks.
- `links[].to` is a project slug or `project/task` id. Types:
  `depends-on`, `follow-up`, `related`. Links are stored on one side only;
  the CLI computes reverse links ("blocked by", "referenced by").
- `artifacts[]` holds metadata because HTML and JSON files have no
  frontmatter. `about` and `why` may be empty; never invented.

### Log — `log.md` (project and task)

One line per event, appended by the CLI:

```
- 2026-10-15 14:02 status doing -> done | PR 102 merged
- 2026-10-15 13:40 artifact scale-design.md | How the rate limiter behaves...
- 2026-10-15 11:10 note | Rate limiter conflicts are transient; retry fixes it
```

Every write command appends its own event. `2b log` adds a free note.
The user never writes the log by hand. Weekly views are built from these lines.

## Rules

Rules are instructions for agents at three levels: global, project, and
task. The more specific level wins: task > project > global.

Each level has a `rules.md` with one rule per line. A rule can have a key
in brackets:

```
# global rules.md
- [tsc] This Mac has 8 GB RAM. Run tsc checks one at a time, never in parallel.
- Keep answers short and in plain terms.

# task rules.md
- [tsc] Do not run tsc checks.
```

Merge:
- A keyed rule replaces the rule with the same key at a less specific
  level. In the example, the task gets only "Do not run tsc checks".
- Rules without a key all apply. The merged output labels each rule with
  its level, most specific first, and states: "If rules conflict, the more
  specific level wins."

Agents get rules from `2b rules <task>`. `2b show` includes them, and
`2b run` adds them to the prompt of a recurring agent task. The skill tells
the agent to run `2b rules` before it starts work on a task.

Limit: 2b rules apply only when the agent works through a 2b task. A rule
for every chat in every repo belongs in the global `CLAUDE.md` or
`AGENTS.md`.

## Recurring tasks

Most tasks are normal. A recurring task runs on a schedule.

```yaml
---
title: Daily work digest
kind: recurring
status: doing               # only "doing" tasks are scheduled
every: daily 19:00          # see format below
run: agent                  # agent | command
agent: claude               # claude | codex (for run: agent)
command:                    # shell command (for run: command)
last-run: 2026-10-16 19:00
last-result: ok             # ok | error
---
Rule (the agent prompt): read today's Claude Code, T3 Code, and Codex
sessions. For each piece of work, run `2b log` on the matching task. Put
work with no matching task in today's inbox note.
```

Schedule format: `daily HH:MM`, `weekdays HH:MM`, `mon,wed,fri HH:MM`,
`hourly`. The CLI maps it to `launchd` `StartCalendarInterval`.

Why `launchd`, not cron: it is built into macOS and runs a missed job when
the Mac wakes. Cron skips it.

Mechanism:
- `2b schedule sync` writes one plist per scheduled task to
  `~/Library/LaunchAgents/com.2b.<task-id>.plist` and loads it with
  `launchctl`. It removes plists for tasks that are no longer `doing` or no
  longer exist. `2b status` and `2b new task --every` call it.
- Each plist runs `2b run <task-id>`. `2b run` also works by hand.
- `run: command` runs the command with `/bin/sh -c`.
- `run: agent` runs `claude -p` (or `codex exec`) with the task body as the
  prompt, plus the last error if `last-result` is `error`. The agent may use
  only `2b`, read tools, and the session folders
  (`~/.claude/projects`, `~/.codex/sessions`, `~/.t3/userdata`).
- Every run writes stdout and stderr to `tasks/<task>/runs/<date-time>.log`,
  appends a log line, and sets `last-run` and `last-result`.
- On non-zero exit or timeout (default 15 min): `last-result: error`, a
  macOS notification, and the dashboard shows the task at the top.

Built-in helpers for command tasks:
- `2b notify "<text>"` — macOS notification via `osascript`.
- `2b dash --open` — start the dashboard if it is not running, then open it
  in the browser.

Examples:
- Daily 19:00, agent: update logs from today's sessions.
- Weekdays 14:00, command: `2b dash --open`.
- Daily 10:00, command: `2b notify "$(2b ls --due-before +2d --short)"`.

## CLI

One TypeScript file run by Node (type stripping), no dependencies. Binary
name `2b`. Every read command supports `--json` for agents.

| Command | Effect |
|---|---|
| `2b init` | Create the store and its git repo |
| `2b new project <slug> --area work\|personal [--title ...]` | Create project, print path |
| `2b new task <project> <slug> [--due ...] [--repo ...] [--branch ...]` | Create task with today's date prefix, print path |
| `2b artifact add <task> <file-or-name> --about ... --why ...` | Copy or create the file with a standard name, register it |
| `2b path <project\|task>` | Print the folder path |
| `2b status <project\|task> <status> [--reason ...]` | Change status, enforce reason, log it |
| `2b set <project\|task> <field> <value>` | Set due, deadline, repo, branch |
| `2b add <project\|task> pr\|resource\|link ...` | Append to a list field |
| `2b log <project\|task> "<note>"` | Append a note |
| `2b ls [--status ...] [--area ...] [--due-before ...]` | List projects and tasks |
| `2b show <project\|task>` | Full record with reverse links and recent log |
| `2b find <text>` | Search titles, frontmatter, and file contents |
| `2b week [yyyy-mm-dd]` | Events in that ISO week, grouped by project |
| `2b dump <slug>` / `2b learn <slug>` | Create an inbox or learnings note, print path |
| `2b dash [--port ...] [--open]` | Start the local dashboard; `--open` opens the browser |
| `2b new task ... --every "<schedule>" --run agent\|command [--command ...]` | Create a recurring task and schedule it |
| `2b run <task>` | Run a recurring task now (launchd calls this) |
| `2b schedule sync` / `2b schedule ls` | Sync launchd jobs with the store / list jobs and last results |
| `2b notify "<text>"` | Show a macOS notification |
| `2b rules [<project\|task>]` | Print merged rules with their level |
| `2b rule add <global\|project\|task> [--key ...] "<text>"` | Add a rule; with a key, replace the rule with that key at that level |
| `2b rule rm <global\|project\|task> <key-or-line>` | Remove a rule |
| `2b check` | Report broken links, missing fields, bad names |
| `2b import` | One-time migration (see below) |

Task ids accept a unique suffix, so `2b show permit-recovery` works.

Errors: unknown status, missing reason, unknown link target, and a
duplicate slug all exit with a non-zero code and a one-line message. No
command deletes files.

## Dashboard

`2b dash` starts a Node `http` server on localhost that serves one HTML
page and one `/api/state?week=yyyy-mm-dd` JSON endpoint. Read-only.

Views:
- Failed recurring tasks at the top, with a link to the run log.
- Week picker (default: this week).
- Projects grouped by status, with status reasons.
- Tasks due or overdue.
- Activity for the selected week, grouped by project.
- Click a project or task to see its record, links, artifacts, and log.

## Skill

`skill/SKILL.md` in this repo, linked into the Claude Code and Codex skill
folders. A skill only inside the store would load only when
the agent runs in that folder, and most chats run in repos.

The skill tells the agent:
- "2b", "second brain", "save this", "artifact" → use `2b`.
- Before saving an output, find or create the task, then
  `2b artifact add` with `about` and `why`.
- Before work on a task, run `2b rules <task>` and follow the result.
- On "for this task, never do X" or "globally, always do Y", run
  `2b rule add` at that level.
- On status talk ("pause X because Y"), run `2b status`.
- On "every day at 7pm do X" or "remind me", create a recurring task
  with `--every`, and write the rule as the task body.
- For "what did I do this week", run `2b week --json` and answer in short
  plain terms.
- Never write store files directly except artifact content.

## Migration (`2b import`)

A real move of existing folders into the store. No symlinks.

1. **Scan.** `2b import scan <folder>...` lists every child of each given
   folder with a date guess (folder name, README, or earliest file time), the
   README title and status line, and file counts.
2. **Plan.** The agent writes a plan file: target project per item, new task
   slug, status mapped from the README text, and artifact metadata from
   headings. Loose files go into a task or into `inbox/`.
3. **Approve.** The user reviews and edits the plan. Nothing moves before that.
4. **Move.** Delete `node_modules`, `__pycache__`, and `*.map` (rebuildable).
   Move the files. Write readme and log for each task.
5. **Verify.** Content checksums of every kept file match before and after.
   `2b check` passes.
6. **Clean up.** The user updates old path references and removes the
   emptied folders.
